# Port status, known gaps and deviations

_As of 2026-09-19. Update this file whenever a gap closes or a new one is found._

## Status

Every system of the original Unity game now has Luau behind it (docs 01–16).
The whole tree passes `selene`, `stylua`, `rojo build` and `luau-lsp` strict
analysis (the CI suite in `.github/workflows/ci.yml`).

**Studio testing has only just begun.** 2026-09-19: the uploaded ids resolve and
the images load on the client (`ContentProvider:GetAssetFetchStatus` → `Success`),
and Invisible Man's fallback head is right — but nothing was actually _on screen_
until the same day's fix: every `Decal`/`Texture` was authored on the part's
`Front` face, which in Roblox is **-Z**, i.e. pointing away from the camera at
+Z, and the default Roblox character spawned at the origin in front of lane 0's
frog. Both are fixed (`Face = Back` everywhere; `Players.CharacterAutoLoads =
false` plus a `ReplicationFocus` on the frog body, since this place has instance
streaming on). The evidence for those two is computed (face normals vs. the
camera look vector, a clear raycast from the camera to every frog part), **not
photographic** — Studio MCP `screen_capture` works in Edit mode (it needs a
`capture_id`) but times out in Play mode, so no screenshot has yet confirmed the
frog's own pixels in a run.

The face flip has a horizontal consequence, checked the same day with an
edit-mode capture of a known-asymmetric sprite at ±¼-tile offsets: on `Back` the
image still reads **un-mirrored** from the camera, but the face's U axis runs the
opposite way from `Front` — a **positive `Texture.OffsetStudsU` slides the image
towards -X (screen-left)**, while a positive `OffsetStudsV` slides it up. Only
the pupils use those offsets (`WorldFrogCosmetics`), and they now negate U so the
frog looks _at_ its target; V was already right. Left\*/Right\* parts are
unaffected — nothing in `src/` rotates or negative-scales a part, and the
template's limb X signs match the Unity dump in doc 12 (`LeftLimb` at -X).
Spawn density, lane spacing,
difficulty, UI scaling and how the game feels are still unverified. Each phase
doc ends with a "needs a Studio playtest" list:

- [13-levels-and-lanes.md](13-levels-and-lanes.md#known-risks-needing-a-studio-playtest)
- [14-world-dressing.md](14-world-dressing.md#what-needs-a-studio-playtest)
- [15-menus-and-input.md](15-menus-and-input.md#what-needs-a-studio-playtest)

## Steps only a human can do

1. **Playtest** — `rojo serve`, connect from Studio, play through the Tutorial,
   Pot, Kitchen (200 steps) and Country (500), with two players.
2. **Upload assets** — the `tools/` pipeline (see `tools/README.md`, doc 10).
   Needs an Open Cloud API key with Assets read/write and
   `legacy-asset:manage`. As of 2026-09-19 `tools/asset_ids.json` (gitignored)
   already holds ~100 uploaded ids (`status: resolved-direct`); the remaining
   entries — including the five background/US-map images added the same day —
   are still `id = 0`. Run `tools/write_asset_ids.py` to pull cached ids into
   `SkinAssets` / `SoundAssets`, then spot-check one image in Studio: confirmed
   2026-09-19 via MCP (`HotFrogBody`, `rbxassetid://132401989626297`, on the live
   `Frog_<UserId>`/`BugTemplate` instances during a playtest) — an
   `assetType=Image` upload id loads directly from script, on both server and
   client, no `--resolve-only` re-upload needed. Note that a non-zero `Texture`
   property is **not** proof the art is visible: these same instances were
   invisible for a day because their decals faced away from the camera (see
   Status above).
3. **Create products** and paste ids:
   - 4 Game Passes → `src/shared/SkinCatalog.luau` (`gamePassId`)
   - Fly-pack Developer Products → `FLY_PRODUCTS` in
     `src/server/SkinService.server.luau`
   - 10 badges (10…100 steps) → `src/shared/Badges.luau`
4. **Enable** "Studio Access to API Services" (DataStores) and publish.

## Deliberate deviations from Unity

| Decision | Unity | Port | Why |
|---|---|---|---|
| Level progression | never advanced past Pot (`nextLevelIndex` written, never read) | Pot → Kitchen at 50 steps, Kitchen → Country at 100 (`Config.LEVEL_THRESHOLDS`) | Kitchen/Country were built but unreachable; owner's choice. Thresholds changed from 200/500 to 50/100 on 2026-09-22 (b-20260922-101937-mcaj, owner's decision: a new level every 50 steps) |
| Multiplayer field | local split-screen, one field per controller | one **lane** per player, side by side along X (doc 13) | per-player levels and sideways travel are impossible on a shared field |
| Spawner `Movements` offsets | off-screen staging points dragged on screen by the continuous per-frame pull | converted to studs with a fixed aspect assumption and **clamped**. Step X uses the portrait half-width, `Config.SPAWN_VIEW_HALF_WIDTH` ≈ 8.84 studs; scenery uses the lane half-width. A vertical-direction spawner clamps X to the view half-width, and a side spawner clamps it to the lane edge + 3. `Lane.clearSpot` moves a spawn that would land within `Config.SPAWN_GAP` (1.5 studs) of another step's grab box back along its travel line, up to 12 studs, and drops it if nothing is clear | the port pulls per grab, not per frame, so an off-screen spawn would be recycled before it was ever seen. The clamped point is now a staging point off-screen or at its edge: new steps start beyond the camera band and slide in on the pull (see the next row) |
| Spawner time per grab, and the pull | the pull (`SpawnManager.PullStep`/`PullVector`) is a per-frame force scaled by the grabbed step's distance from a target line, so a grab drags that step most of the way to it; spawners run a fixed 1 s per grab (`Step.cs` Pull: `Invoke("StopPull", 1f)`), and new steps enter from off-screen staging points on that scroll | **Owner's ruling (b-20260921-164409-nkkh, b-20260921-164429-ee9c, b-20260921-152825-fzl6), replacing the old fixed 6-stud pull:** a grab pulls the grabbed point (the step's centre, or `GripOffset` for the carrot), measured where it will rest once running pulls finish, to the point of its travel line nearest `Config.PULL_TARGET` (the lane origin, which is the camera centre): `PullMath.pullDistance`, clamped to [`PULL_MIN_DISTANCE` 2, `PULL_MAX_DISTANCE` 24] studs, over `PullMath.pullTime` = distance / 40 clamped to 0.25-0.6 s. Pulls are eased (Sine Out) displacements played by `Lane.advanceMotions` on the server's Heartbeat. They add up instead of per-step tweens cancelling each other, and a step spawned mid-pull rides what is left. Each grab earns `Config.PULL_SPAWN_WINDOW` = 1 s of spawner time, as in Unity, spent at once in `Lane.spawnForPull`. Each spawn's rest point is its staging point carried along the travel direction by the share of the pull still to come. The part is then created further back by whatever the running pulls still owe, and pushed further out when needed so its whole extent starts outside the ±15.7-stud camera band (`Lane.entryShift`, plus 0.5 studs; for pure sideways travel the same half-extent is used as an assumed half-width). The pull then carries it into view, so steps slide in rather than pop up, including tall `Rocket`/`Balloon` art (this closes the old "Tall steps pop IN at spawn" gap). `Lane.clearSpot` spaces spawns by rest positions, and `isOutOfBounds` only recycles a step once both its current and its rest position are out. `prefill` (run start, Tutorial → Pot) and the Tutorial's one-shot ladder batch slide in together from off-screen over `Config.SLIDE_IN_TIME` (0.6 s, `GameServer.slideIn`). The Tutorial retry pull-back is now up to 3 × `PULL_MAX_DISTANCE`, still capped at net pull | The port pulls once per grab instead of per frame, so the destination is computed rather than reached by a force. A per-stud spawn rate (8 studs per spawner-second) suited the old fixed pull. With target-seeking pulls, a grab consumes about one step whatever its length, and Unity's fixed window does too. Headless sim (20 runs × 50 grabs, 0.7 s cadence; the bot grabs the nearest portrait-visible step ahead): grabs with no such step went from 168 to 103 of 1000 on Pot, 375 to 303 on Kitchen and 423 to 257 on Country, against the per-stud rate under the same pull. There were 0 spawn overlaps, and 0 spawns started with any of their extent inside the view in portrait or landscape. The grabbed point ended 0.5-1 stud from the centre along the travel line. Caveat: Kitchen and Country still leave about 30% of grabs with no step visible ahead in the sim's strict portrait metric (the landscape Studio view shows more). Before this change, spawns surfaced inside the top of the view just after each grab. |
| Classic run mode (owner's request b-20260921-164458-8liv) | no such mode: the world only scrolls while a grab's 1 s pull runs (`Step.cs` `Invoke("StopPull", 1f)`), and `Rigidbody2D` drag 2 stops the steps soon after | a per-run **Mode** picked on the main menu (`MenuClient` "Mode: Classic/Normal/Tutorial" button, cycled Classic -> Normal -> Tutorial, sent as `StartRun`'s one argument, validated in `GameServer`, stored as `Lane.mode` and the lane folder's `Mode` attribute). **Classic is the default** (b-20260921-182325-3jtz); only an explicit Normal opts out, and a missing or invalid mode falls back to Classic. Normal is the per-grab pull above, unchanged. Classic keeps it and adds a constant scroll along the lane's spawn direction (`Lane.drift`, every Heartbeat) at `Config.CLASSIC_SCROLL_SPEED`: Pot 10, Kitchen 13, Country 16 Unity u/s (≈3.14 / 4.09 / 5.03 studs/s), none in the Tutorial. It starts on the first grab (the same `canFall` gate as gravity) and stops when the frog dies. Every `CLASSIC_CHUNK_TIME` (0.5 s) the drift is settled as one chunk: it earns `CLASSIC_SPAWN_PER_STUD` (1/8, the port's old per-stud rate) spawner-seconds through `Lane.spawnForPull` (so spawns start off-screen and drift in), and it is replicated as one `PullDelta` so scenery and backdrop scroll along. In Classic a held step whose grip point sinks below `LAVA_Y`, or leaves the lane's ±`LANE_HALF_WIDTH`, is force-released, so a frog that stops climbing is carried into the lava and dies | the owner wanted a mode where "the steps keep falling even when they aren't grabbed". Classic's scroll speed ramps the longer the run's drift has run (`Lane.driftElapsed`; `Config.CLASSIC_SCROLL_ACCEL_RATE` = 1/120 of the level's base speed per second, capped at `Config.CLASSIC_SCROLL_MAX_MULT` = 3x base), about doubling after ~2 minutes; it carries across level changes and resets every run. Tutorial never drifts. Not tuned by feel. The speeds are scaled from Unity's own pull: `PullStep`'s force 2·\|40 − y\| is 80 at the centre, and with drag 2 it settles at 40 u/s. Classic uses a quarter of that on Pot. Checked in Studio: the held step drifted at 3.2 studs/s with no input, the run ended when the step reached the lava, and Normal mode did not drift. Not yet tuned by feel |
| Steps kept out from under the Roblox PlayerList (owner's decision b-20260921-182502-qgbw, reopening b-20260921-152729-o03u) | no such thing: Unity has no platform overlay over the field | `GameClient` estimates the core PlayerList's rectangle (top-right, under the top-bar inset, ~340 px wide, 4 + 42 + 8 px plus 40 px per player, capped at 440 px; `Config.PLAYERLIST_*`, measured off the live CoreGui list) and sends it in lane-relative studs over a new `ScreenObstruction` remote, only on change (polled every 0.5 s) and never while spectating. `GameServer` validates it (finite, min < max, no bigger than the lane's view, clamped to it, own lane only, updates under 0.2 s apart dropped) and, on each grab, `Lane.obstructionExtra` lengthens the pull (never shortens it) by the smallest amount up to `OBSTRUCTION_MAX_EXTRA_PULL` (8 studs, about one ordinary pull) that leaves no step's grab box (`HitSize`/`HitOffset`, padded 0.25) resting inside it, or the fewest when none clears within the cap.

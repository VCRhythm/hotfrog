## What this repo is

A Roblox (Luau) port of HotFrog, a Unity 2D physics climber. Two codebases share the root:

- **Unity C# original** — the root-level folders `Core/`, `Player/`, `Entities/`, `Spawning/`, `Input/`, `Store/`, `UI/`, `Audio/`, `Ads/`, `Utility/` (+ `HotFrog.asmdef`). This is **read-only reference**, not something to build or edit. Luau files cite the C# file they port (e.g. `Player/Frog.cs`); read it when a behaviour question comes up. The rest of the Unity project (prefabs, audio clips) lives outside this repo.
- **Roblox port** — `src/` (Luau, synced by Rojo per `default.project.json`), `docs/roblox-port/` (design docs 01–17), `tools/` (Python asset pipeline), `Sprites/` (source art).

`docs/roblox-port/17-status-and-known-gaps.md` is the status page: what is done, open gaps, human-only steps, and every **deliberate deviation from Unity**. Check it before "fixing" something that looks unfaithful to the original, and update it when a gap closes or a new one appears.

## Commands

Toolchain is pinned in `rokit.toml` (`rokit install`): rojo, stylua, selene, luau-lsp. There is no unit-test suite; "tests" are the CI checks below plus playing in Studio.

```sh
rojo serve                                   # live-sync into Studio (Rojo plugin -> Connect)
stylua --check src/                          # format check (stylua src/ to fix)
selene generate-roblox-std                   # one-time; writes roblox.yml (gitignored)
selene src/                                  # lint
rojo build default.project.json --output build.rbxl
bash tools/luau_check.sh [files...]          # luau-lsp type-check, defaults to src/; pass one file to check just it
```

CI (`.github/workflows/ci.yml`) runs all four: stylua, selene, rojo build, and `luau-lsp analyze` against a generated sourcemap. `tools/luau_check.sh` is the local equivalent of the last one (it finds luau-lsp in `~/.rokit/tool-storage` and adds `--no-strict-dm-types`). Source files are `--!strict`; keep them passing strict analysis.

Asset pipeline (run from the repo root; details, flags and credential setup in `tools/README.md`):

```sh
python tools/build_manifest.py               # scan Sprites/ + the external Unity Audio dir -> tools/asset_manifest.json
python tools/upload_to_roblox.py --manifest tools/asset_manifest.json --dry-run
python tools/upload_to_roblox.py --manifest tools/asset_manifest.json   # resumable; caches to tools/asset_ids.json
python tools/upload_to_roblox.py --status    # moderation state
python tools/write_asset_ids.py              # rewrites the Ids tables in SkinAssets.luau / SoundAssets.luau in place
```

The `Ids` tables in `src/shared/SkinAssets.luau` and `SoundAssets.luau` are **generated by `write_asset_ids.py`** — change keys/ids through the pipeline, not by hand. Credentials come from `.env` (gitignored; template in `.env.example`); the manifest, id cache and `.asset_cache/` are gitignored too. `python tools/luau_exec.py --script "..."` runs Luau headlessly in the published place (Open Cloud Luau Execution).

## Architecture

### Rojo mapping

`src/shared` → `ReplicatedStorage.Shared`, `src/assets` → `ReplicatedStorage.Assets` (clone templates as `.model.json`), `src/server` → `ServerScriptService.Server`, `src/client` → `StarterPlayerScripts.Client`, `src/workspace/PlayField.model.json` → `Workspace.PlayField`. `bugloop/` is mapped in as well (in-game bug reporter feeding `.bugs/`; `bugloop/Config.luau` is gitignored and machine-local; `HttpEnabled` is on for it). File suffix decides the class: `.server.luau` Script, `.client.luau` LocalScript, plain `.luau` ModuleScript.

### Server authority

The client sends **intents** (`GrabStep`, `ReleaseStep`, `StartRun`, …); the server owns all state — frogs (custom gravity, limbs, death, respawn), steps, the pull/scroll, score, run state, level flow. Frog models are server-owned and replicate, which is what makes multiplayer work. `GameServer.server.luau` get-or-creates every RemoteEvent under `ReplicatedStorage.Remotes` at startup; the remote list with payloads is at the top of that file.

Server scripts never `require` each other. They talk through get-or-create `BindableEvent`s in `ServerStorage` (`AwardFlys`, `SpawnBugAt`, `BugCaughtServer`) so load order doesn't matter, and through attributes on `workspace.PlayField.Lanes`.

### Lanes (doc 13)

Each player gets their own play field "lane", offset along X only (`Config.LANE_SPACING`; slots `0, 1, -1, 2, …` so the first lane is at the origin). `src/server/Lane.luau` is pure per-player logic (spawn direction, spawner state, level index, run progress, bounds, weighted kind picks, spawn positions); `GameServer` owns the pooled step Instances, the frog simulation and scoring, and drives each `Lane` on Heartbeat. `workspace.PlayField.Lanes/<UserId>` folders with `UserId` / `Origin` / `Level` / `RunState` attributes are the discovery contract for `BugService` and all client scripts. Every active step and bug carries a `LaneUserId` attribute, and grab/catch remotes reject mismatches.

A lane's `spawnDirection` is the direction the **world scrolls**, the opposite of the frog's apparent travel. The port pulls once per grab (a tween), not per frame like Unity — several deviations in doc 17 follow from that.

### Data-driven content

- `Levels.luau` — level data (Tutorial → Pot → Kitchen → Country; thresholds in `Config.LEVEL_THRESHOLDS`), step and scenery spawners with their `Movements` lists already converted to studs (`UNITY_TO_STUDS ≈ 0.3143`; derivation in doc 13 and the comment above the level list). Spawner `direction` fields are Unity's literal values and are matched **by sign only**.
- `StepKinds.luau` — one entry per Unity step prefab → behaviour, sprite stem, spawn probability. `StepBehaviors.luau` — the `ActionType` registry dispatched by `GameServer` through a `ctx`.
- `SceneryKinds.luau` / `WorldConfig.luau` — client-only cosmetics data; `Config.luau` — gameplay tuning.
- Level/spawn numbers trace back to the Unity prefab dumps in docs 11 and 12; treat those docs as the source of truth for values.

### Persistence

`Profiles.luau` owns the single DataStore and per-player schema (best score, Flys, skins, receipts, gift cooldown, `tutorialDone`, `musicOn`) plus the `OrderedDataStore` leaderboard mirror. Services read `Profiles.get(player)` and react to `Profiles.Loaded`; none opens its own store. Flys are granted only by firing `ServerStorage/AwardFlys` (applied and replicated by `SkinService`).

### Client

`GameClient` handles input, the camera (centred on the local lane) and the HUD; `MenuClient` the run-state UI (Menu → Playing → Dead); `LevelClient` republishes `LevelChanged` as attributes + a BindableEvent under `LocalPlayer.LevelState` for the cosmetics scripts. The `World*.client.luau` scripts (doc 14) are purely cosmetic and must not move server-owned parts — they read replicated attributes/remotes only (e.g. pupils are `Texture` offsets; "which step is this limb holding" is inferred by `world/GrabTarget.luau` from limb positions). Scenery, frog cosmetics and tutorial specks render for every lane; backdrop, lava, touch indicator and quality popups for the local lane only.

### Art and audio binding

`SpriteSkin.apply(root, skinName?)` textures any `Decal`/`Texture`/`ImageLabel` by attribute: `Sprite = "<stem>"` (skin-agnostic, via `SkinAssets.image`) or `Suffix = "<suffix>"` (per-skin frog part, via `SkinAssets.part`, which falls back to the shared `Universal` art, then Hot Frog's). A frog stem is the skin name without spaces plus the suffix (`"Hot Frog"` + `Body` → `HotFrogBody`), matching filenames under `Sprites/Frogs/<name>/`. An id of `0` is a silent no-op for both `SpriteSkin` and `SoundFX.play`, so unuploaded assets never error.
